# Архитектура Qadam (ADR-002)

Статус: принято 18.10.2026. Заменяет ADR-001 (разделение на четыре роли): там работа шла по людям, здесь по параллельным сессиям Claude Code в worktree.
Владелец файла: интегратор.

## 1. Что оптимизируем
Порядок взят из критериев жюри (docs/TASK.md):
- **Релевантность.** Жёсткие фильтры (дистанция, часы, ограничения), затем ранжирование. Ответ даёт LLM, но только по найденным кандидатам.
- **Контекст.** Время, погода, бюджет времени, дети, доступная среда, ночь. Всё это явно передаётся в фильтры и в ответ.
- **Объяснения.** У каждой карточки есть «почему», «что делать», время, источник и уверенность.
- **UX.** Демо понятно с первого экрана: пресеты сценариев, карта, маршрут.
- **Этика.** Сервер получает только H3-ячейку, есть честные метки и запасной путь без LLM.
- **Завершённость.** Eval на 15 сценариях и документы, собранные из реального кода.

## 2. Решения и альтернативы

| # | Решение | Альтернативы | Почему так |
|---|---|---|---|
| D1 | Векторный индекс в памяти: numpy, косинус | Qdrant, pgvector, FAISS | В Астане ~2–5 тыс. POI, полный перебор занимает меньше 5 мс. Без инфраструктуры, работает на Windows и в Docker одинаково. Пересмотреть, если POI станет больше 100 тыс. или понадобится несколько инстансов. |
| D2 | Один сервис FastAPI отдаёт и API, и `web/` (чистый JS + Leaflet) | Streamlit; React/Vite | Настоящее веб-приложение, без сборщика, один деплой, полный контроль над UX. Streamlit выглядит шаблонно, React — лишний тулчейн на сутки. |
| D3 | Факты считает код, текст пишет LLM; валидатор и шаблонный запасной путь | Всё делает LLM | Нет галлюцинаций в расстояниях и часах. Демо не падает без квоты (критерии 1, 3, 6). |
| D4 | Приватность: в браузере координаты переводятся в H3-ячейку (с 19.10 — r10, ≈0,015 км², решение Megah; раньше r9), сервер не принимает lat/lon (`extra="forbid"`, тест) и ячейки мельче r10 (`schemas.MAX_H3_RES`, тест) | Округление координат; хранение с согласием | Минимизация по закону РК № 94-V. Это наглядно в демо: рисуем ячейку на карте. |
| D5 | Claude через `anthropic` SDK: `claude-sonnet-5-5`, запасная `claude-haiku-5-5`; structured output в Pydantic (`messages.parse`), дисковый кэш. Эмбеддинги — Gemini (google-genai), по желанию, только при `GEMINI_API_KEY` | Gemini для всего (прежняя версия D5); OpenAI; локальные модели | Решение команды 18.10: ключ Anthropic. У Anthropic нет API эмбеддингов, поэтому векторный индекс опционален, а без него retrieval лексический (запасной путь заложен в D1/D3). Модели задаются в .env, проверка — `scripts/check_env.py --llm`. |
| D6 | Основа — OSM (Overpass), плюс Wikidata; LLM-описания с пометкой | 2GIS, Google Places | Сбор автоматизирован, лицензия ODbL. 2GIS запрещает хранение. Google Places — опция позже. |
| D7 | Контракт до кода + дорожки в worktree + интегратор | Все правят всё; разбиение по людям | Параллельная работа без конфликтов, у каждого файла один владелец (§6). |

## 3. Поток RAG
```
браузер: запрос + (ориентир | GPS→H3 r10) + фильтры + время (+ route_profile, prefs — 1.3.0)
   │  POST /api/recommend  (RecommendRequest: без координат)
   ▼
resolve_origin ─► parse_query (LLM ⟶ rules) ─► apply_overrides ─► QueryIntent
   │                                                     │
   ▼                                                     ▼
SearchContext: центр ячейки, местное время UTC+5, погода (Open-Meteo), radius_for(intent)
   │
   ▼
retrieve: жёсткие фильтры (дистанция, категории, дети, коляска, помещение, часы, ночь)
        → релевантность (cosine по эмбеддингам | лексика)
        → скор = Σ WEIGHTS × части → MMR-разнообразие → top-8 Candidate
   │
   ▼
draft_cards (Claude, JSON по схеме)  ── LLMUnavailable / use_llm=false ──► template_cards
   │
   ▼
finalize: id ∈ кандидаты, факты из Candidate, «открыто сейчас» только при open/high, метки
   │
   ▼
plan_route (≥2 карточки) ─► DataUsed + warnings + disclaimer ─► Answer (1–3 Card + MiniRoute)
```

## 5. Форматы данных
- `data/processed/poi.jsonl`: по одному `POI` на строку, UTF-8. Коммитится в git, чтобы во всех worktree были одни данные.
- `data/index/embeddings.npy` (float32, N×D, L2-норма), `ids.json` (тот же порядок), `meta.json` (`model`, `dim`, `count`, `created_at`, `doc_template`).
- `data/landmarks.json`: список `Landmark`. Координаты приблизительные, пока у записи `verified: false` (их сверяет DATA).
- Пешеходный граф (волна 5, контракт DATA → FEATURES). Строит `pipeline/walk_graph.py` из OSM (тротуары, дорожки, переходы), читает `app/walkgraph.py`. Новых зависимостей нет: только numpy и heapq.
  - `data/processed/walk_graph.npz` (`numpy.savez_compressed`). Номер узла — номер строки в массивах узлов.

    | Массив | Тип | Смысл |
    |---|---|---|
    | `node_lat`, `node_lon` | float32 | координаты узла |
    | `node_flags` | uint8 | биты: 1 переход, 2 светофор, 4 занижённый бордюр, 8 переход без разметки, 16 бордюр известен и не занижен (kerb=raised/rolled; волна 8), 32 разметка известна (crossing=marked/zebra/uncontrolled или crossing:markings не no; волна 8) |
    | `edge_u`, `edge_v` | int32 | концы ребра (номера узлов); граф неориентированный, каждое ребро один раз, `u != v` |
    | `edge_len_m` | float32 | длина ребра по линии OSM, метры |
    | `edge_flags` | uint8 | биты: 1 лестница, 2 освещено (lit=yes), 4 пешеходная дорожка, 8 крупная дорога, 16 отрезок перехода, 32 не освещено (lit=no; волна 8) |

  - `data/processed/walk_graph_meta.json`: `osm_snapshot` (дата снимка OSM), `bbox` `[юг, запад, север, восток]`, `nodes`, `edges`, `crossings`, `signals`, `largest_component_share` (доля узлов в крупнейшей компоненте до отбрасывания мелких, 0..1; в npz остаётся только крупнейшая), `poi_nodes` (`{poi_id: номер узла}`), `landmark_nodes` (`{landmark_id: номер узла}`), `created_at`. Данные — производная OSM под ODbL.
  - Время по графу: `walk_min = ceil(длина пути / 75)`, минимум 1 (те же 4,5 км/ч, но без множителя 1,3). Вид перехода в `RouteCrossing.kind`: бит 2 → `signals`, иначе бит 8 → `unmarked`, иначе бит 32 → `marked`, иначе `unknown` (с 1.3.0; до волны 8 бит 1 без 2 и 8 читался как `marked`, а у 34 % переходов тип в OSM не указан).
  - `walk_graph_meta.json` может содержать `format_version` (сейчас 1; другое значение → прямые отрезки; поле необязательно), `steps_edges` (число рёбер-лестниц) и `license` («ODbL 1.0, © участники OpenStreetMap»).
  - Правила чтения (FEATURES/T91 и eval):
    - точка привязывается к узлу не дальше 150 м; `poi_nodes` / `landmark_nodes` используются с той же проверкой, иначе ближайший узел; дальше 150 м → для этой точки прямой отрезок;
    - если прямая между двумя точками не длиннее суммы их привязок (обе привязаны к одному или соседним узлам далеко от точек), отрезок считается по прямой, а не через узлы;
    - ребро с битом 16 (отрезок перехода), у которого ни на одном конце нет узла-перехода, считается переходом с неизвестной разметкой (`unknown`; до волны 8 — `unmarked`);
    - ночью бит 2 (lit=yes) — плюс, но отсутствие бита — «освещённость неизвестна», а не «темно»: в OSM Астаны lit размечен у ~3% рёбер. Множитель для рёбер без бита 2 не больше ×1,1, иначе маршрут тянется к редким размеченным кускам;
    - длина ребра по линии OSM может быть меньше хорды по float32-координатам до ~1 м: строгую проверку «длина ≥ хорды» не делать.
    - в графе бывают узлы-переходы степени 1 (тупиковые хвосты переходов в OSM) и рёбра короче 1 см (совпадающие узлы OSM): читатель их терпит.
  - `MiniRoute` 1.1.0: `path_source` (`graph` | `straight`), `crossings` (до 50), `steps_count` (число отрезков-лестниц). При `graph` в `path` и `legs` путь и время по графу.
  - Флаг `WALK_GRAPH` (по умолчанию включён) работает, если файл есть (`settings.walk_graph_ready`). Флаг выключен, файла нет или любая ошибка загрузки и поиска → прежние прямые отрезки и `path_source=straight`.
  - Волна 8: биты node 16, node 32 и edge 32 добавочные, `format_version` остаётся 1. Нет бита — «нет данных», никогда не «да»: ребро без битов 2 и 32 идёт в `unknown_lit_share`, переход без битов 4 и 16 — в `kerb_unknown`, переход без битов 2, 8 и 32 — `unknown`. У перехода бордюр берётся с его линии footway=crossing, один итог на переход: 16, если хоть с одной стороны не занижен, иначе 4; 4 и 16 вместе не бывают.
  - Стоимость рёбер по профилю (T121): переход: `fastest` — с разметкой +10 с, `unknown` +20 с, без разметки +40 с; `accessible` — лестницы запрещены, с разметкой +10 с, `unknown` +60 с, без разметки +120 с, светофор +5 с, бордюр без данных +15 с, высокий +120 с; `lit` — lit=no ×3, без данных ×1,2, освещено ×1. Правило «не больше ×1,1» выше — про ночной режим `fastest`, оно не меняется. `plan_route` и `plan_walk` принимают `profile=` аргументом: он заменяет `Mode.profile`, профиль только внутри `Mode` будет прочитан как `fastest`.
- Контракт 1.3.0 (волна 8, `app/schemas.py`). Все новые поля необязательные, запросы и ответы 1.2.0 остаются валидными.
  - Запрос: `route_profile` — `fastest` (по умолчанию) | `accessible` (без ступенек) | `lit` (по освещённым улицам).
  - Запрос: `prefs` (`UserPrefs`) — `likes` и `avoids`, каждый до 8 меток. С 1.3.1 у списков разные словари: `likes` только из `LikeTag` (подписи `PREF_LIKE_LABELS_RU`), `avoids` только из `AvoidTag` (`PREF_AVOID_LABELS_RU`); `PREF_LABELS_RU` — оба вместе.

    | Список | Метка | Подпись | Что значит для подбора (FEATURES уточняет по eval) |
    |---|---|---|---|
    | likes | `quiet` | тихо | тег `quiet` |
    | likes | `coffee` | кофе | тег `coffee`, категория `cafe` |
    | likes | `kids` | с ребёнком | тег `kids`, `kids_friendly` |
    | likes | `museums` | музеи | категории `museum`, `gallery` |
    | likes | `parks` | парки | категория `park` |
    | likes | `warm` | в тепле | `indoor`, короткие отрезки на улице |
    | likes | `night` | ночные | теги `night`, `late_open`, `24_7` |
    | avoids | `bars` | бары | без категорий `bar`, `nightlife` (в 1.3.0 это была метка `no_bars` в likes) |
    | avoids | `noisy` | шумно | штраф местам с `live_music`, категориям `bar`, `nightlife`, `entertainment`, `mall` |
    | avoids | `long_outdoor` | долго на улице | короткие отрезки на улице, как у `warm`, но без требования «в помещении» |
    | avoids | `kids_places` | детские места | штраф `playground` и местам с тегом `kids` |
    | avoids | `cafes` | кафе | без категории `cafe` и тега `coffee` из разбора текста (чип «Без кафе») |

    Прежняя метка `no_bars` в `likes` читается как `bars` в `avoids` (`DEPRECATED_LIKES`, синоним на одну версию, до 1.4; решение Megah 21.10), без 422. Неизвестная метка, метка чужого списка (в том числе `no_bars` в `avoids`), свободный текст, повтор, одна метка в обоих списках, противоречивая пара из `PREF_CONFLICTS` (`kids` + `kids_places`, `coffee` + `cafes`), лишнее поле → 422. Истории нет: сервер не хранит prefs. В логах prefs не пишутся вместе с ячейкой, ориентиром и запросом; в `repr` запроса их нет (`repr=False`).
  - Запрос: `exclude_poi_ids` — для чипа «Ещё» (REQUEST UX, решение пользователя): до 9 id уже показанных в этой серии карточек (`osm:…`, `event:…`, формат как у `POI.id`), без повторов; иначе 422. Сервер не показывает эти места снова; если без них ничего не подходит — обычный пустой ответ. Только на один запрос, не хранится; в `repr` запроса нет, в лог вместе с ячейкой и запросом не пишется.
  - `MiniRoute`: `profile` — профиль, по которому маршрут построен на самом деле. `lit_share`, `unlit_share`, `unknown_lit_share` — доли длины пути по графу (OSM lit=yes / lit=no / нет тега), задаются вместе, в сумме 1 (±0,02); у прямых отрезков 0 / 0 / 1. `kerb_lowered`, `kerb_unknown` — число переходов на всём пути с занижённым бордюром и без данных о бордюре (список `crossings` обрезан до 50, поэтому «высоких» из него не вычислять); у прямых отрезков `None`. `max_outdoor_leg_min` — самый длинный отрезок пешком между остановками, минуты. `steps_count` — как в 1.1.0. Всё считает код. Если `accessible` пришлось идти со ступенями (без них пути нет или он длиннее больше чем на 30 %), `profile` остаётся `accessible`, `steps_count > 0`, причина в `note`. `steps_count` считает ступени только на участках по графу: если часть пути прямыми отрезками (это сказано в `note`), «без ступенек» не утверждать. Освещённость — данные OSM, а не обещание безопасности.
  - `Card.kind`: `place` (по умолчанию) | `event`. У события обязательны `starts_at` (с часовым поясом, UTC+5) и `source_url` (только `https://`), `ends_at` необязателен и позже начала; у места эти три поля пустые. Для события `poi_id` = id события, `title` — название, `address` — площадка и адрес, `geo` — точка площадки, `facts_sources` — `manual`. «Идёт сейчас» — только если `starts_at ≤ сейчас < ends_at` и оба известны, иначе «начало в ЧЧ:ММ». Само `kind=event` и есть метка «временное».
  - Подбор волны 8 (T123, FEATURES):
    - `route_profile` передаётся в `plan_route`/`plan_walk` аргументом, минуты карточек — с тем же профилем. `overrides.wheelchair=true` при `fastest` включает `accessible`. Строка в `filters` «маршрут: без ступенек / по освещённым улицам» — только если маршрут по графу построен этим профилем (для `accessible` — без ступеней), иначе «запрошен маршрут …».
    - prefs: каждая метка из `likes` +0,25 (всего не больше +0,30), из `avoids` −0,25 (не больше −0,35) — штраф, не фильтр; `no_bars` убирает `bar` и `nightlife`. В `filters`: «предпочтения: …; избегать: …». Явное «избегать» важнее разбора текста: метка из `avoids` убирает из разобранного намерения свои категории и теги (coffee → cafe, museums → museum и gallery, parks → park), а её слова в запросе не дают совпадения по словам; категории из `overrides.categories` остаются. В `Answer.intent` — то, что спросили.
    - «В тепле» включают `likes` с `warm`, `overrides.indoor_only` или мороз ≤ −10 °C (Open-Meteo); `warm` в `avoids` выключает. Остановки только в помещении, до каждой и между ними не больше 10 мин пешком, без петли; меньше двух мест в помещении — уличные места с предупреждением. Явный `max_walk_min` не урезается.
    - `exclude_poi_ids` отсекаются в retrieval до скоринга и до отбора Claude, места и события; в `filters` только число «без уже показанных мест: N». Честно пустой подбор — «Других подходящих мест рядом нет: уже показанные не повторяем.»
    - События (`app/events.py`): пустой, отсутствующий или битый файл — событий нет, без ошибки. Без `ends_at` событие длится 2 ч, но не дольше 24:00 своего дня. Берутся события, которые не закончились и начинаются сегодня или в ближайшие 6 ч; событие — кандидат с теми же фильтрами (+0,08), площадка уступает место своему событию. «Идёт сейчас» — только при `starts_at ≤ сейчас < ends_at`, и никогда у события дольше 12 ч (выставка, фестиваль: «проходит до 30.11 18:00»). Время на другой день всегда с датой. Summary от LLM может сказать «идёт сейчас», только если идёт каждая карточка-событие. Время визита — из события, не от модели. Сломанная запись события не роняет подбор мест.
  - `data/events.json` (DATA → FEATURES): список объектов `id` (`event:<slug>`), `title` (`ru`, по возможности `kk`, `en`), `venue`, `address`, `geo` или `venue_poi_id`, `category`, `tags` (из `TAG_VOCAB`), `starts_at`, `ends_at` (ISO с `+05:00`), `source_url` (https), `source_name`, `fetched_at`. Добавочно (T122): `price` ({min, max, currency: KZT} или null), `indoor`, `kids_ok`, `venue_bound_by`; `geo` есть всегда; `ends_at` может быть null. Вход — `data/manual/events.json` (вносят люди), источники только из `data/manual/event_sources.json` (домен, условия, дата проверки), сборка `python -m pipeline.events`. Только источники, чьи условия разрешают хранение; 2GIS и Яндекс нельзя. Прошедшие события отбрасываются при сборке, а FEATURES ещё раз фильтрует их на время запроса.
- Контракт 1.3.1 (волна 8.1, решения Megah 21.10). Все новые поля необязательные.
  - `MiniRoute.straight_share` — доля длины пути, посчитанная прямыми отрезками (0 — весь путь по графу, 1 — весь прямой). «Без ступенек» утверждается только при `path_source=graph`, `steps_count=0` и `straight_share=0`; разбор текста `note` для этого не используется.
  - `Card.venue` — название площадки, только у события; `address` — адрес площадки.
  - Профиль `lit` в интерфейсе — «Ночью — по крупным улицам»; имя `lit` в API оставлено для совместимости. CORE предпочитает рёбра вдоль крупных улиц (edge бит 8) и штрафует lit=no. Слово «освещённые» в интерфейсе не используется; строка об освещении в итоге маршрута — только при `route.profile=lit`.
  - Событие и маршрут: если до начала события больше 30 мин, оно не остановка маршрута, а блок «Вечером рядом» со временем начала; если событие — остановка, то последняя, с пометкой «к ЧЧ:ММ». Источник события в интерфейсе — «Из афиши» и домен `source_url`, не «Из базы мест».
  - Режим «Доступная среда» (`overrides.wheelchair`) сам включает профиль `accessible` и пишет это в `filters`.
  - Погода: прогрев на сегодня при старте сервера, тайм-аут запроса 1,5 с; не успели — ответ без погоды и строка в «Какие данные использованы» (`data_used.weather`). Погоду на живом API не подменяем: мороз на демо показываем только на моке.
- `data/raw/`, `data/cache/`: не коммитятся.
- API:
  - `GET /api/health`;
  - `GET /api/landmarks`;
  - `GET /api/meta`;
  - `POST /api/recommend` → `Answer`, при неверном вводе 422.

## 6. Как работаем параллельно (Claude Code)
**Основа.** Контракт написан до кода (`schemas.py`, заглушки, фикстуры, мок `Answer`). Поэтому все дорожки стартуют одновременно и не ждут друг друга. У каждого файла один владелец (таблица в CLAUDE.md), значит при мерже почти нет конфликтов.

| Механизм Claude Code | Для чего у нас | Когда |
|---|---|---|
| **Десктоп: «+ New session» с галкой worktree** (Ctrl+N) | Длинные дорожки DATA, CORE, LLM, WEB, EVAL. Пользователь видит и направляет каждую. Worktree лежат в `.claude/worktrees/`. `.env` копируется через `.worktreeinclude`. | Волны 1 и 3 |
| **Субагенты с `isolation: worktree`** (`.claude/agents/*-engineer.md`) | Короткие независимые задачи на 15–40 мин из одного окна интегратора. Результат возвращается сводкой: ветка, коммиты, REQUEST. | Волна 3, мелкие доработки |
| **`/batch <инструкция>`** | Много однотипных мелких правок (i18n-строки, докстринги, типизация). Каждая правка в своём worktree. | По необходимости. Требует git и, для PR, GitHub-remote |
| **`/subtask`**, субагенты Explore | Побочные исследования (формат SDK, библиотека opening_hours) без засорения контекста. | Всегда |
| Agent teams (экспериментально) | **Не используем.** Участники команды работают без worktree, расход токенов выше, на Windows только in-process. | — |

**Ветки и база.**
- Основная папка всегда на `main`.
- `.claude/settings.json` → `worktree.baseRef: "head"`: новые worktree и субагенты ответвляются от локального `main`, даже если не всё запушено.
- Дорожки забирают обновления командой `git merge main`.
- В main вливает только интегратор: скилл `/integrate`, перед ним агент `merge-reviewer`.

**Ревью.**
- Встроенный `/code-review` проверяет дифф на баги.
- `/ecc:python-review` и `/ecc:fastapi-review` смотрят стиль и паттерны.
- `@agent-ecc:rag-pipeline-reviewer` проверяет качество RAG.
- `@agent-ecc:silent-failure-hunter` ищет проглоченные ошибки в запасных путях.
- `/security-review` запускаем перед публикацией (нужен origin).

## 7. Риски и что с ними делаем
| Риск | Что делаем |
|---|---|
| Лимиты, отказ (`refusal`) или недоступность Claude | Запасная модель (Haiku), server-side fallback, дисковый кэш пресетов, путь `use_llm=false`. Баланс API пополнить заранее. |
| Нет эмбеддингов (нет `GEMINI_API_KEY`) | Лексическая релевантность в retrieval; качество проверяем eval. Ключ Gemini можно добавить позже без изменения кода. |
| Неверные имена моделей или форма вызова SDK | `scripts/check_env.py --llm` и `scripts/check_llm.py` в первый же час, модели задаются в .env. |
| Overpass перегружен | Зеркала, повторы, кэш `data/raw/`, фикстур ≥ 40 POI (T10) в первые 40 минут. |
| Мало часов работы в OSM | Честное `unknown/low` и предупреждения. В слайде об ограничениях: план с партнёрскими данными. |
| Конфликты при мерже | Один владелец на файл, контракт меняет только интегратор, маленькие коммиты. |
| Нет времени на видео и слайды | EVAL-дорожка пишет документы параллельно с кодом. Код-фриз — утром 19.10. |
